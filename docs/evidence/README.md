# Evidence registry (U7 claim-to-evidence gate)

Every claim in `docs/CLAIMS.yaml` cites an evidence record by ID, and
every record points at a committed run artifact whose SHA-256 is
recorded in the registry and in the claim. `scripts/check_claims.py`
re-hashes every artifact on every run; a mismatch fails the gate.

## Layout

- `registry.json` — the index: `evidence_record_id` →
  `run_artifact` (path) + `run_artifact_sha256`. Schema:
  `textforensics.evidence-registry/v1`.
- `runs/EV-YYYYMMDD-<kind>.json` — the run artifacts. Schema:
  `textforensics.run-artifact/v1`. Each artifact records the exact
  command, environment, repo git SHA, detector version (when the run
  exercises the detector), run date, measured `results`, and a `drops`
  manifest.
- `report-card.md` — generated by the gate (`check_claims.py
  --report-card`). It leads with the worst-slice human false-positive
  rate and lists failed claims. Never hand-edit it: the gate
  regenerates it and CI diffs it.

## Rules the gate enforces

1. **Every claim carries `evidence_record_id` + `run_artifact_sha256`.**
   A claim without either fails.
2. **Hash re-check.** The gate recomputes each artifact's SHA-256 and
   compares it against the registry and the citing claim. Mismatch
   fails. Editing an artifact without refreshing its record is a
   gate failure, not a silent update.
3. **Numbers from the registry.** Claims with a `numbers` map have
   each metric compared against the cited record's `results` (within
   `tolerance` when given), and the claim statement must contain the
   numbers. Hand-edited numbers fail.
4. **Staleness.** A `verified` claim whose record is more than 90 days
   old, or whose record carries a `detector_version` different from
   the current builtin detector version, fails as `stale`.
5. **Drops manifest.** An artifact without a `drops` key is
   `incomplete` and its claims fail. An empty list means nothing was
   dropped. Skipped tests, unmeasured Python versions, and known host
   flakes are recorded here, never silently omitted.

## Badge vocabulary

Adapted from the ACM artifact badges (see the Phase 3 research
report §3.1). In-repo meanings:

- `available` — the artifact is committed and hash-verified.
- `functional` — the gate re-ran the artifact's command successfully.
- `reproduced` — an independent run (CI on the same head) reproduced
  the numbers. Seeded records start at `available`; do not claim
  `reproduced` without a matching CI run.

## Refreshing records

Records are immutable evidence of one run: never edit an artifact
in place. To refresh, run `scripts/seed_evidence.py` (it re-runs the
measurements, writes new artifacts with new IDs, and rewrites
`registry.json`), then update the citing claims' `evidence_record_id`,
`run_artifact_sha256`, and `numbers` to the new values, and regenerate
the report card. The gate verifies the new linkage.

## Worst-slice human FPR

The report card leads with the worst-slice human false-positive rate.
There is currently no human-FPR evidence recorded (Phase 5 release
gate), so the card honestly reports `unknown` until U1/dataset runs
produce real measurements. Never invent an FPR.
